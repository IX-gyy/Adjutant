# 赫尔墨斯记忆核心 & TODO 系统 实现文档



## 一、架构概览



本项目为桌面 AI 语音助手（泰伦帝国副官）引入了**双层记忆体系**与**云端驱动的结构化任务系统**，核心设计原则是：  

- 本地 3B 量化模型（Qwen2.5）专注于角色扮演与对话流畅度。  

- 云端智谱 GLM-4-Flash 负责高精度记忆提取与待办意图解析。  

- 记忆持久化至 ChromaDB 向量库，待办落盘 SQLite。  

- 时间信息贯穿全链路，使 AI 具备时间感知能力。


---



## 二、赫尔墨斯记忆核心（长期记忆 + 短期记忆）



### 2.1 记忆分层



| 记忆类型 | 存储位置 | 生命周期 | 说明 |

|----------|----------|----------|------|

| 短期记忆 | Python 内存列表 `chat_history` | 当前会话 | 最多保留 20 轮对话，超出自动截断，每条附加时间戳 |

| 长期情景记忆 | ChromaDB 向量库 | 持久化 | 由 GLM 从对话中提取的关键事实、事件、约定 |

| 事件/属性语义 | ChromaDB（通过标签分类） | 持久化 | 区分“指挥官属性”、“指挥官事件”、“约定”三类条目 |



### 2.2 短期记忆格式化



- 为准确传递给本地模型，每条历史消息均格式化为可读文本：

- **用户消息**：`[2026-05-11 15:23:01] 指挥官: 我今天有体育课`

- **副官消息**：`副官: 已为您标记，指挥官。`（不加时间戳，防止模型模仿输出）

- 此格式化仅在构建 LLM 上下文时使用，实际对话记录仍为 JSON 格式并持久化到 `history.json`。



### 2.3 长期记忆提取流程



1. **触发条件**  

 - 每 N 轮对话自动提取（`MEMORY_EXTRACTION_INTERVAL=1`，当前每轮触发），或  

 - 用户消息包含关键词：“记住”、“别忘了”、“提醒我”、“记下来”、“备忘”等。  



2. **提取过程（异步线程）**  

 - 将本轮用户消息和副官回复打包，加入提取队列。  

 - 后台线程调用**智谱 GLM-4-Flash**，请求分析对话并提取：  

   - 指挥官属性（如“指挥官是大三学生”）  

   - 关键事件（如“下周有考试”）  

   - 约定/期望（如“请每天提醒我跑步”）  

 - 所有提取结果附带**对话发生时间**，并返回 JSON。  



3. **记忆存储**  

 - 每条记忆存入 ChromaDB，附带元数据 `timestamp`（Unix 时间戳）。  

 - 存储前进行**相似度去重**（`difflib.SequenceMatcher` 阈值 0.8），防止重复写入。  

 - 记忆文本格式包含时间信息，例如：  

   - `指挥官属性：指挥官是大学三年级学生 [时间: 对话发生日期]`  

   - `约定： [2026-05-11 17:07] - 请提醒指挥官明天下午四点去上体育课`  



### 2.4 长期记忆检索与注入



1. **检索时机**：每次构建本地 LLM 上下文时，以用户当前消息作为查询，从 ChromaDB 进行向量相似度检索（距离 < 1.5），最多返回 3 条。  

2. **分类注入**：将检索结果分为三类（属性、事件、约定），分别拼接到系统提示中：

 ```

 【关于指挥官的已知信息】

 - 指挥官是大三学生

 【指挥官近期的关键事件】

 - 本周六上午10点有一个会议

 【指挥官与副官的约定/待办】

 - 明天下午四点提醒上体育课

 ```

3. **时间感知**：系统提示首部始终注入当前日期时间（格式：`2026年05月12日 星期二 15点30分`），使本地模型能理解“今天”、“明天”等相对表述。

## 三、结构化 TODO 系统（云端解析 + 本地执行）



### 3.1 设计理念



- **本地模型完全不参与 TODO 操作**，其 system prompt 不含任何任务标记说明，只保留角色设定和记忆规范。  

- 所有待办**识别、时间计算、过期检测**均由 GLM-4-Flash 统一完成。  

- 后端根据 GLM 返回的结果直接执行数据库操作，并构造固定的两段式角色回复。  



### 3.2 TODO 触发机制



- 用户消息通过**关键词列表**进行初筛（“提醒”、“别忘了”、“待办”、“计划”、“有什么事情”、“日程”、“安排”等）。  

- 命中关键词后，消息**不再交给本地 LLM**，而是启动独立线程运行 `handle_todo_request()`。



### 3.3 GLM 统一分析接口 (`analyze_todo_and_memory`)



- 该方法部署于 `MemoryManager` 中，单次 API 调用同时完成：  

1. **记忆提取**（返回记忆条目，自动存入 ChromaDB）  

2. **TODO 意图识别**（返回操作类型：`add` 或 `list` 或 `null`）  

- 输入包含当前完整时间、用户原文，以及数据库已有的待办列表（用于过期判定）。  

- 返回标准 JSON：

```json

{

  "memories": [...],

  "todo_action": {

    "type": "add" | "list" | null,

    "items": [{"content": "...", "due_date": "2026-05-12 16:00"}],

    "expired_ids": [3, 5]

  }

}

```



### 3.4 TODO 操作类型详解



1. **添加（`add`）**  

 - GLM 从用户表述中提取待办内容和截止时间（格式 `YYYY-MM-DD HH:MM`，默认为上午9点）。  

 - 后端调用 `TodoManager.add_todo()` 写入 SQLite，并向前端推送 `todo_added` 事件。  

 - 回复示例：“已为您添加待办事项：明天下午四点去学院楼开会。”



2. **列表查询（`list`）**  

 - GLM 会收到当前所有待办清单，并比较 `due_date` 与当前时间，自动标记过期的 ID。  

 - 后端先执行过期 ID 的删除（`delete_todo`），再返回有效待办。  

 - 回复示例：“您当前的事项如下：1. 写完实验报告（截止：2026-05-12 23:59）…… 以下已过期事项已自动归档：昨天的晨跑提醒。”



3. **无操作**  

 - 若 GLM 判定无需任何 TODO 动作（`todo_action` 为 `null`），后端仅做记忆提取，并返回一句固定确认语。



### 3.5 删除策略与安全措施



- **自动删除**：仅针对 GLM 在查询时识别出的过期事项，且必须在 `due_date` 严格小于当前时间时执行。删除前会将内容告知用户。  

- **手动删除**：用户在前端面板直接点击删除按钮，调用 `delete_todo` 指令，完全不经过自然语言解析，杜绝误删。  

- **对话驱动删除**：暂不开放模糊名称匹配的语义删除，避免模型错误判断导致数据丢失。



### 3.6 对话流实现（两条固定回复）



当用户发出 TODO 类意图时，后端生成两条连续的副官消息：



1. **过渡语句**（固定文案）：  

 “正在翻阅您的行程计划，指挥官，请稍等……”  

 前端以逐字流式效果展示，并伴有 TTS 播报。  

2. **结果确认**（由 GLM 返回的动作动态构造，但仍是后端生成文本，不经本地 LLM）：  

 例如：“已为您添加待办事项：…” 或 “您当前的事项如下：…”。  

 同样流式推送到前端并 TTS 播报。



这两条消息均作为 `assistant` 角色存入对话历史，其内容由后端完全控制，确保表达准确、风格统一。



### 3.7 前端联动



- `todo_added`、`todo_list`、`todo_updated` 事件保持原有协议，前端可据此刷新待办面板。  

- 查询待办时，后端除发送结果消息外，也会推送 `todo_list` 事件，使面板同步更新。  

- 手动操作（面板添加/删除/完成）仍通过原有指令（`add_todo`, `list_todos`, `complete_todo`, `delete_todo`）进行，绕过 GLM。

## 四、技术要点与优化



- **异步非阻塞**：GLM 调用在独立线程执行，不阻塞主指令循环，避免拖慢整个应用。  

- **错误降级**：若 GLM 调用失败或 API Key 未设置，后端会给出友好错误提示，并可以退回到本地 LLM 普通回复（不丢失对话功能）。  

- **时间精度**：全链路（记忆时间戳、待办 due_date、系统当前时间）统一使用 `2026年05月12日 星期二 15:30` 格式或 Unix 时间戳，保证一致性。  

- **成本控制**：记忆提取与 TODO 解析合并为单次 API 请求，减少调用频率；同时利用关键词触发避免无效消耗。  

- **状态安全**：处理 TODO 时同样持有 `generation_lock` 并使用 `transcribe_substate` 为 `"generating"` 锁定，防止用户重复提交。
